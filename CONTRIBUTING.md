# Contributing to AgentMD

Maintain one compact general-purpose policy for completing the user's actual work. Preserve the eight-file layout: AGENTS.md, README.md, this file, four generic model-binding TOMLs and the evidence registry. Do not add model-specific Markdown, fixed occupations, skills or an evaluation service.

## Decision contract

- State the objective, task-grounded acceptance conditions and limits. Compare changes against the current configuration doing the same work with the same checks. This logical baseline is not a measured performance result and does not require a cheap model to fail first.
- Choose the next feasible action, not a globally best model. Jointly consider model and effort, current evidence/context, tools, permissions, remaining cost and latency. Include primary/worker execution, transfer, checks, integration and rework. Treat cost and time separately unless user preferences supply a defensible tradeoff; never invent monetary weights or calibrated success probabilities.
- Preserve adequate verified progress. Escalate for an identified capability demand, consequential uncertainty or useful contribution. A failed check can call for a local correction or missing information rather than another model. No fixed ladder, highest-score default, mandatory cycle or automatic downgrade after a hard stage.
- Buddy is temporary overlap at a justified model/effort transition, not per-task division. Select the candidate from the same LUT. The incumbent and candidate actively solve/test the same remaining problem at a bounded checkpoint, exchange actual evidence in both directions, compare against common requirements and choose the supported approach and continuing lead. Retain an adequate incumbent when no material advantage is demonstrated. End the other active solve and confirm cessation or isolation of conflicting writes before transferring write ownership. Finish if acceptance is established; otherwise preserve the selected lead's existing context. The primary remains the coordinator and owns accounting, authorization and acceptance; workers request later transitions through it. Where overlap/exchange/continuation is unavailable, disclose the feasible fallback. Isolate competing writes, confirm safe ownership transfer and verify the integrated artifact. No separate ranking, fixed pair, recursive spawning or repeated routine debate.
- Worker status must report acceptance evidence on identified artifacts. Essential unverified conditions remain UNCERTAIN; model agreement and a PASS label cannot replace checking. Do not narrow or silently change acceptance conditions to manufacture success.

## Recovery accounting

Before recovery or duplicate solving, declare a finite task-scoped allowance sized to task scope and user/runtime constraints. No universal numeric default or claim that the chosen allowance is optimal. The primary reserves centrally; each additional local/worker/parallel recovery or duplicate solve consumes one slot when started. Initial work on genuinely distinct requirements and necessary non-repeated checks is outside this count.

One overlapping candidate solving the same requirement uses one additional slot; an authorized continuation of the incumbent or selected approach is not a new attempt. Two new recovery attempts use two. Model, effort, thread, hypothesis, blocker or label changes cannot replenish the task allowance. Record explicit user scope/budget revisions. Do not disguise a second attempt on an unresolved requirement as new first-pass work.

Authorize first-pass scope separately from recovery slots and classify assigned/returned solves as INITIAL or RECOVERY/DUPLICATE. One approach ends at its planned acceptance checkpoint; a new correction after failure or a replacement approach is a new attempt. Do not count routine tool calls as attempts or hide unlimited local revisions in one attempt.

Before retrying failed setup, declare a finite task-scoped setup-retry allowance. Classify first setup, retry or continuation from observed history, not the existence of an allowance. Unknown usage remains UNKNOWN until reconciled; do not rely on an unverified remaining count. Initial setup is not a retry; log failures and resources. Reserve and consume each retry on dispatch. Failed launches do not show failed competence. Track all worker dispatches, including INITIAL, by assigned scope and available handle. If a reply is ambiguous, retain ownership and any reservation; reconcile the execution and confirm safe replacement before redispatch or conflicting replacement. Release a solving reservation only after confirming that dispatch never started and cannot later start. Started work remains consumed after interruption. Do not repeat unchanged failures or checks without a relevant new reason. When no unreserved recovery allowance remains, prohibit new counted starts, not already authorized continuations within other limits. Preserve artifacts, report unresolved conditions when no permitted correction remains and continue eligible work. This may leave useful corrections undone. It bounds counted actions only if followed, not all time/spend or eventual completion; hard limits require runtime enforcement.

## Evidence updates

Record evidence in [research/benchmark-evidence.md](research/benchmark-evidence.md) before changing the runtime LUT. Preserve exact model/effort IDs, source/version/date, task population, harness, metric definitions, resource denominators, ties and unknowns. Distinguish a published protocol's task/repeat counts from verified compliance of an individual run. State missing hardware, clocks, batch and uncertainty instead of inventing them.

The active LUT preserves every measured model/effort configuration: eight component vectors in none/low/medium/high/xhigh/max order and separate historical broad index/cost/time references. Check all 176 component values and all 22 broad entries against the registry. No unsupported none value becomes zero. Do not silently update selected rolling time values within an older snapshot.

Do not remove candidates using component quality and broad composite resource proxies. A descriptive frontier over declared numbers is not a task-specific or conditional-recovery frontier. Compare matched conditions; do not transfer max-effort scores to lower efforts, count components/composites as independent evidence, treat overlapping intervals as equivalence, or infer conditional rescue/correlation from marginal scores. Missing data are not failure. Provider examples stay illustrative and may not override adequate current work.

Changing model bindings requires evidence of client availability, not merely a published benchmark row. Markdown cannot grant tools or override runtime permissions. Preserve honest limitations when actual resolution is not observable.

## Repeated audit and release

Keep a concrete issue ledger: defect, counterexample, repair, recheck, remaining limitation. Separate three passes: logical identification and objective/units; execution/accounting/ownership; regression after fixes. Re-review affected rules after a newly discovered defect. Stop this scoped audit when the actionable findings have been repaired and the follow-up checks expose no new material issue; this is not proof of universal correctness. A user's explicit request for repeated review is not a mandate for every future task to use an auditor.

Verify syntax and facts with an actual TOML parser; exact names/IDs, common worker contract and absence of fixed effort; the eight-file layout; relative links; numeric transcription; consistency across policy and README; and the runtime byte count with room for project guidance. Check the installer syntax and existing-file protections without installing into a real user profile. Preserve unrelated user guidance.

Use counterexamples and scenario walkthroughs for simple success, cost/time conflict, sunk handoff costs, mixed resource populations, conditional rescue, invalid settings, incumbent/candidate concurrent work, reciprocal evidence exchange, retention of a suitable incumbent, transfer to a selected worker, later transitions from that worker, unavailable continuation, stale checks after integration, superseded work, uncertainty, parallel reservation, interrupted solves, relabeling, exhausted recovery, distinct initial work and explicit scope changes. A small reference calculation can test arithmetic and accounting invariants; it cannot test model compliance.

Only an actual supported-client trace can establish loaded instructions, resolved model/effort, concurrent progress or enforced limits. Comparative performance claims require matched task outcomes and resources. Do not turn ordinary user work into an experimental program. Keep changes reversible and report what changed, what was checked and what remains unknown.
